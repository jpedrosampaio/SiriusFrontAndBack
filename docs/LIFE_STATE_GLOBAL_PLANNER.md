# Unified Life State and Global Planner

## Pre-implementation audit (main 25bcc84d72a490c5995f558695720e6cc93996a2)

`ai/planning.py::plan_day` is the existing deterministic daily allocator. `Core.get_daily_plan` and `SiriusAgent.daily` currently call it with tasks and calendar commitments only. Study plans already determine **what** to study on each date using canonical StudyPlanEntry, preparation evidence and Adaptive Strategy; they do not assign wall-clock start times. This phase extends the same allocator and preserves that operational allocation.

User.timezone/preferences, Task/TaskInstance, CalendarEvent, StudySchedule, StudyPlanEntry, WorkoutPlan/Day/Session/Log, nutrition aggregates, Goal/Habit checks and financial Decimal ledgers already exist. CalendarEvent can persist explicitly accepted time allocations with source identity and metadata. ActivityReceipt plus the user transaction lock already serialize confirmed writes. No new ledger, planner table, provider or migration is needed.

Current assistant snapshots are read-only but cover only four summary totals. Agent read tools expose each domain separately, and its next study block does not compete for time. Calendar projects fixed commitments but originally filters by start date, omitting overnight overlaps. Domain adapters will emit typed states, candidates and constraints; the coordinator alone combines them. They must not call each other.

## Intended contracts

Bounded owner-scoped daily state; PostgreSQL aggregates rather than full histories. Canonical dated study blocks remain authoritative and are not regenerated by the global engine. Existing fixed commitments, timed tasks and study schedules reserve capacity. Date-locked study blocks stay on their date. Unknown activity durations require an explicit user estimate. Habits, nutrition targets, goals and monthly bills without real due dates remain facts rather than invented urgent appointments.

Availability is user-declared, not inferred from the absence of events. The same daily allocator serves Calendar and Agent. What-if is read-only. Accepting a preview requires an exact snapshot, explicit confirmation and an idempotency key; only new calendar allocations are saved. It never completes a task, pays a bill, changes XP or rewrites a study/training plan. Existing accepted allocations reserve capacity and cannot be moved by preview acceptance.

Priority uses overdue/due dates, explicit task priority, protected dated study blocks and stable source IDs. Reasons and duration origins accompany every recommendation. AI explains supplied facts; it does not provide priority scores. Truncated temporal constraints fail closed. Civil-time days containing an offset transition must not receive automatic allocations until a supported precise time model is available.

## Published API contract (Phase8 PR35)

- GET `/api/life/state`: typed `LifeState`, today or at most 30 days ahead in the account timezone. SQL repeatable-read snapshot, eight independent adapters, 200 candidates/domain and 1000 temporal records/adapter. Truncation suspends allocation. Task completion joins cover actual once-only dates, including old overdue tasks. No full historical bank is fetched.
- PUT `/api/life/availability`: explicit seven-day free windows (up to four/day), optional user duration estimates and a selected owned training plan with explicit weekdays. Existing account preferences remain intact. No availability is presumed when unset.
- POST `/api/life/simulate`: optional capacity, exclusions and duration estimates; no writes. Date-locked study blocks cannot be excluded or resized. Existing StudySchedule minutes cover dated canonical book allocations before additional study is proposed, preventing two schedules for the same work.
- POST `/api/life/accept`: explicit confirmation, typed allocations, owner-bound snapshot fingerprint and mandatory idempotency key. The user lock serializes commits; changed facts or edited allocation fields return409. Scenario-only windows cannot be accepted as real availability. New CalendarEvent allocations reuse stable candidate/source IDs; repeats cannot duplicate accepted work or XP.
- DELETE `/api/life/allocations/{event_id}?confirmed=true`: explicit idempotent release of an owned future global allocation only. Fixed/manual commitments and started history cannot be selected. Original module records remain unchanged; reorganization requires a new simulation and confirmation.

`ai/planning.py::plan_day` is still the sole clock allocator. It supports disjoint free windows, subtraction of every temporal constraint, earliest remaining five-minute boundaries, contiguous blocks and explicit unresolved items. Conflict display is capped at50 with a truncation flag; capacity still uses every constraint, avoiding quadratic conflict payloads. Overnight calendar events are projected into each covered civil day. Core/Agent use the same coordinator and bounded prompt summaries; display truncation never truncates the allocator's constraint inputs.

Preparation emits existing dated blocks rather than recomputing Adaptive Strategy. Training uses a selected owned plan/day or a real active session, never an invented progression. Financial state uses Decimal strings for recorded monthly flows, unpaid monthly bills and budget counts; net is not a bank balance. Monthly bills lack daily due dates and therefore cannot become invented urgent payments. Nutrition uses shared recorded aggregates and explicitly distinguishes existing default targets. Habit and goal review candidates need user durations; reviewing a goal does not claim progress. No service can pay, transfer, complete, award XP or change source histories through this planner.

Limitations: no optimizer promises perfect schedules; stable factual ranking and first-fit produce explainable proposals. No automatic multi-day redistribution of operational study dates. Unknown fixed-task durations and DST transition days suspend allocation. Unscheduled work remains visible. Declared training inclusion does not choose an exercise progression or rewrite the workout session UX. No new infrastructure, dependencies or migration; schema remains a81c9d37e502.

Review corrections: a non-repeating StudySchedule occurs on the first selected weekday on or after its account-local creation date, rather than only on the creation day. The legacy schema has no explicit occurrence-date field; this rule is disclosed and does not create another recurrence. Coverage association is performed by the coordinator after collecting all fixed constraints. If a study slot conflicts with another study slot or any other domain, canonical durations remain untouched and planning is suspended; overlapping nominal durations are never counted as usable coverage. Only nonconflicting fixed study slots cover dated notebook work.
