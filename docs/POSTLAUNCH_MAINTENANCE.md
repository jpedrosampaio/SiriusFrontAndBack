## Workout contract and compatibility

The form now declares modality, location, real apparatus (unknown `null` versus declared none `[]`), level, focus, goal, available minutes, exclusions and frequency. It previews the same deterministic session count used in the request/calendar: single session or 1/4/8/12 weeks, 2–7 sessions per week. A gym preset is an explicit selection; changing location never grants apparatus. Legacy fields/aliases remain accepted when consistent, and saved plans/sessions are not migrated or rewritten.

The provider returns at most three typed complete bases per call, with bounded tutorials; larger legacy splits use successive batches. One corrective retry per batch preserves the same labels and uses a safe reason, not private raw output. The backend checks completeness, apparatus declarations and common named apparatus, declared exclusions, novice complexity/volume, modality, variety, estimated time and a lower bound from prescribed between-set rests. Rejection saves no partial plan or XP. This is a conservative structural validator, not a medical diagnosis or an exhaustive exercise ontology; an external provider's tags/estimated execution duration still require the user's review.

The backend composes exact weeks/sessions and deep-copies prescriptions. Variety comes from distinct bases; weekly stages explain familiarization, consistency and review of actual evidence. Loads remain unassigned/bodyweight and do not rise automatically. Training Intelligence retains the existing stable day-origin requirement for numeric comparison; no cross-day performance is invented. New plan metadata identifies proposals and professional-review needs. Sensitive limitations stay in the owned plan/request, without automatically replacing account preferences or appearing in public plan/day names.

New relative weekly proposals distribute sessions at offsets `floor(i × 7 / frequency)` from the plan's local creation date. The Today card and Life State candidate adapter share the same helper, respect intervals without sessions and the end of the proposed cycle. No Calendar records, fixed commitments or actual sessions are created. Legacy plans keep their previous rotation, and manual execution remains available. Receipts replay before provider work; owner-serialized persistence still commits the plan, XP and receipt together. The UI keeps uncertain retries on the exact in-memory body/key and prevents simultaneous submits; it does not store health drafts in browser storage.

## Analytical dashboard

Accessible Radix tabs at the top select Meu dia or Análises, with keyboard navigation and a non-private URL view preference. The existing Command Center and detailed dashboard remain the sources. The inactive view unmounts; Home queries are disabled during analyses, and analysis/panel requests consume cancellation signals. Graphs remain intersection-triggered, reject stale window responses and expose loading/failure/retry. Refresh uses the existing owned query cache/invalidation and canonical endpoints.

Financial aggregates stay Decimal through JSON decimal strings and exact BRL display; chart coordinates use approximate JS numbers while tooltips retain original strings. Registered monthly/weekly net flow is labelled as a recorded result, not bank balance. Absent goals, attempts, question accuracy and incomplete/absent declared workout calorie totals remain unknown. Recorded zero stays zero. Only completed workouts/studies count; nutritional records may contain estimates, and unconfirmed targets stay unset. Existing exam scores remain their sourced normalized 0–100 scale, distinguished from aggregate accuracy and raw weighted points.
